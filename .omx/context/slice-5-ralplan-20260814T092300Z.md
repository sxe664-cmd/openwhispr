# 2. Architecture Decision

## Decision

Use **direct reuse of AIReceptionist Python/domain behavior through a narrow, typed Electron adapter**, not direct reuse of its renderer or Electron main process.

### Canonical model

Define one target-facing `CalendarEvent` shape, based on:

- Source `AppointmentEvent`: `receptionist/reminders/models.py:12-40`
- Safe source feed: `receptionist/desktop_config.py:401-487`
- Target `CalendarEvent`: `src/types/calendar.ts:11-25`

Required canonical fields:

```text
provider
calendarId
eventId
eventUid
occurrenceId
summary
startTime
endTime
timezone
allDay
status
recurrence metadata
attendees
conferenceUrl
calendarUrl
capabilities:
  canSendEmail
  canSendSms
  canRename
  canCancel
  canReschedule
```

`LocalEncounter` remains a separate lifecycle projection containing note ownership, recording state, transcript linkage, and encounter lifecycle.

## Identity

Use one stable occurrence identity:

```text
provider + calendar_id + event_id + start_iso
```

Recurring occurrences, tombstones, cancellation, and reconciliation must use this identity. Do not maintain separate source, bridge, and renderer IDs.

## Bounded query

All calendar reads must use:

```text
[startInclusive, endExclusive)
```

Rules:

- Home: current local calendar day only.
- Day: one local day.
- Week: selected local week.
- Month: selected month, with bounded visible range.
- Maximum row limit enforced in main/sidecar.
- No renderer-side “load everything then filter.”
- Tombstones reconcile only complete bounded windows.

The current target `getEncounters(limit)` query at `database.js:3650-3671` must not remain the Home data source.

# 6. Acceptance Criteria and Test Matrix

## Calendar/navigation

- Day view queries exactly one local day.
- Week view queries exactly seven local days.
- Month view renders all days in the selected month and only displays events in the bounded query.
- Previous/next/today navigation changes the query range and never requests an unbounded list.
- Event count and empty copy correspond to the selected range.
- Recurring events and cancelled occurrences retain stable identity.
- Existing local Apple/Microsoft calendar behavior remains intact.

## Event cards/actions

- Real source events render title, local timezone time, duration, attendee count, recurrence/status, and safe links.
- Email action is unavailable when no valid attendee/contact email exists.
- SMS action is unavailable unless backend confirms consent, channel preference, non-suppression, and valid phone.
- Send actions show pending, success, retry, and failure states.
- Rename, cancel, delete, and reschedule resolve the canonical stored event.
- Offline mutation failure never removes the cached event or local encounter.

## Templates

- Pre-appointment email/SMS templates load from validated config.
- Unknown variables are rejected.
- Post presets support `thank_you_review`, `thank_you_only`, and `book_next_appointment`.
- Channels are independently selectable.
- Timing bounds are enforced.
- Post timing is relative to appointment end.
- Save → restart/reload → read returns the same validated configuration.
- Recent jobs display status and safe suppression reasons.

## OAuth/configuration

- Missing OAuth client produces `setup_required`, not a false connected state.
- Missing/expired token produces explicit authorization state.
- OAuth browser flow is initiated only by main process.
- Tokens never appear in renderer IPC payloads, logs, errors, or DOM.
- Google connection remains AIReceptionist-managed.
- Microsoft and Apple integrations remain available and unaffected.

## Offline/error/success

- Cached local events remain visible when sidecar/network sync fails.
- No cached data produces a clear empty/unavailable state.
- Runtime unavailable, timeout, invalid JSON, invalid config, OAuth denial, and provider failure each map to fixed safe error codes.
- Successful sync updates `lastSuccessfulSyncAt`.
- Reminder failure does not erase successfully projected calendar events.
- No placeholder response returns success for an unimplemented action.

## Save/reload

- Receptionist settings validate before write.
- Invalid settings leave the previous valid configuration unchanged.
- Save creates/retains the source backup behavior.
- Restart-required status is visible.
- Email/template/post-follow-up settings persist across reload.

## Timezone boundaries

Test at:

- Local midnight.
- UTC date differing from local date.
- DST spring-forward.
- DST fall-back.
- All-day events.
- Event ending exactly at range end.
- Event starting exactly at range start.
- Month/week crossing year boundaries.

## Home filtering

- Home contains only encounters whose start belongs to the current local calendar day.
- Yesterday, older completed, and future encounters do not appear on Home.
- History/Search still find older encounters and linked notes/transcripts.
- In-progress current-day encounters remain visible.
- A completed current-day encounter remains visible until the day changes.
- Offline cached Home filtering uses the same local timezone rules.

## Regression

- Existing notes save/open.
- Existing meeting recording/transcription/diarization remains functional.
- Local model selection and BYOK remain functional.
- Apple Calendar and Microsoft Calendar remain functional.
- Existing history, note search, command search, and transcript flows remain functional.
- No OpenWhispr Cloud/account/billing/workspace surface is reintroduced.

# 7. Risks, Alternatives, and No-Placeholder Rules

## Risks

1. **Duplicate Google authority:** legacy target tables/managers remain alongside the managed bridge.  
   **Mitigation:** runtime startup audit; one active Google sync/OAuth path; preserve Apple/Microsoft separately.

2. **Timezone/recurrence drift:** source event IDs and target occurrence IDs diverge.  
   **Mitigation:** canonical compound identity and boundary tests.

3. **Home history leakage:** current `getEncounters(limit)` is unbounded by date.  
   **Mitigation:** bounded SQL query, not renderer filtering.

4. **Credential leakage:** private seed, OAuth tokens, or Python output enter renderer/logs.  
   **Mitigation:** main-only runtime env, fixed serialized errors, packaging scan.

5. **Source UI overclaim:** source Day/Week/Month is a date-grid/list filter, not a complete time-grid.  
   **Mitigation:** explicitly implement and test required target presentation.

6. **Config write regressions:** YAML persistence can invalidate existing runtime configuration.  
   **Mitigation:** validate-before-write, backup, reload tests.

## Explicit rules

- No empty arrays presented as successful parity.
- No fake event cards outside test fixtures.
- No fake “connected” OAuth state.
- No success toast when an operation is intentionally unavailable.
- No renderer-side credentials, raw notes, phone numbers, or child logs.
- No direct source Electron renderer embedded in OpenWhispr.
- No removal of local notes, encounters, transcripts, diarization, models, BYOK, Apple, Microsoft, or other third-party integrations.

# 8. ADR

## Decision

Adopt AIReceptionist Python as the authority for Google Calendar, OAuth, reminder delivery, consent, templates, and appointment mutations. Integrate it through typed Electron main-process adapters. Build the user-facing calendar/receptionist experience as React components in OpenWhispr. Store safe calendar projections and local encounter lifecycle in OpenWhispr’s existing SQLite database.

## Drivers

- One Electron shell.
- Local-first operation.
- Existing source behavior is already tested and security-sensitive.
- Existing target local encounter/note architecture must survive.
- Avoid duplicate OAuth/sync and Cloud/account/workspace reintroduction.

## Alternatives considered

1. Embed source renderer/Electron app — rejected due duplicate shell and monolithic non-reusable UI.
2. Rewrite all Python behavior in TypeScript — rejected due duplicated provider, consent, scheduling, OAuth, and config logic.
3. Keep current bridge only — rejected because it lacks real UI, actions, templates, OAuth setup, receptionist settings, and bounded Home behavior.

## Why chosen

The adapter model maximizes reuse of tested source behavior while keeping target ownership of React presentation, local encounter persistence, and Electron lifecycle.

## Consequences

- Requires a typed contract between Python and Electron.
- Requires explicit source feed range support.
- Requires migration/audit of existing target calendar paths.
- OAuth remains invisible to React except for safe setup/status states.
- Calendar UI must be implemented rather than copied wholesale.

## Follow-ups

- Add a source/target contract version.
- Add fixture-driven cross-repository parity tests.
- Add packaging scan that fails on credentials in public builds.
- Add a future full calendar time-grid only if product requirements exceed the source month-grid/list behavior.
