# Encounter Patient Folders Roadmap

## Requirements summary

Turn calendar encounters into patient-centered records while preserving the existing encounter/note lifecycle.

- Create or reuse a patient folder for confidently identified one-on-one encounters.
- Use normalized email as the canonical patient identity; use the name only as the folder label.
- Support an optional deterministic metadata block in the calendar description.
- Never use an LLM or fuzzy name matching to decide patient identity.
- Keep ambiguous, group, missing-email, and conflicting encounters in `Meetings` or `Unassigned` until confirmed.
- Keep patient folders in the private space by default.
- Name completed notes with the encounter date plus a very short focus, while preserving the full transcript and clinical outputs.

## Current repository facts

- Starting an encounter reuses an existing note or creates a meeting note from the calendar summary in `src/helpers/database.js:3795-3909`.
- Calendar events currently persist summary, timing, and attendee JSON in `src/helpers/database.js:3517-3545`.
- The managed AIReceptionist calendar projection exposes attendee emails but currently discards attendee display names and raw descriptions in `src/helpers/receptionistCalendarBridge.js:48-101`.
- The Google sidecar reads event descriptions for structured email/phone reminder workflows in `vendor/ai-receptionist/receptionist/reminders/calendar_google.py:226-244` and `vendor/ai-receptionist/receptionist/reminders/identity.py:30-44`.
- Recording completion writes the canonical transcript and marks the encounter completed in `src/helpers/database.js:4282-4344`.
- Clinical summary/SOAP output is stored separately from the canonical note in `src/helpers/database.js:696-730` and generated by `src/helpers/clinicalOutputGeneration.ts`.

## Recommended architecture

Add a local `patient_profiles` table rather than making a folder name the identity:

- `id`
- normalized `email` with a unique constraint when present
- `display_name`
- optional normalized `phone`
- `folder_id`
- `identity_source` such as `attendee_email`, `structured_description`, or `manual`
- timestamps

Add an optional patient reference to encounters. The patient profile owns the stable relationship; the folder remains the user-facing organization and can be renamed safely.

Patient folders should be created in the private space only. Do not automatically place patient records in team/shared spaces.

## Implementation phases

### Phase 1 — Identity contract and parser

1. Define the machine-readable calendar block:

   ```text
   [OpenWhispr Patient]
   name: Alex Morgan
   email: alex.morgan@example.com
   phone: +1 555 123 4567
   [/OpenWhispr Patient]
   ```

2. Parse only exact labeled fields. Reject duplicate or conflicting values.
3. Keep the description human-readable outside the block.
4. Add tests for valid blocks, missing fields, duplicate fields, conflicting email values, malformed email, and phone normalization.
5. Expose only sanitized patient metadata from the AIReceptionist bridge; do not expose raw calendar descriptions to the renderer.

### Phase 2 — Patient data model and deterministic resolution

1. Add the `patient_profiles` schema and migration in `src/helpers/database.js`.
2. Add a shared resolver that:
   - filters the current user/self attendee;
   - accepts exactly one external attendee for automatic assignment;
   - prefers an exact normalized attendee email;
   - uses structured description email only as a fallback;
   - treats conflicting email sources as unresolved;
   - never matches on name alone.
3. Preserve an explicit resolution status/reason for observability: `matched`, `created`, `missing_email`, `multiple_attendees`, or `conflict`.

### Phase 3 — Atomic encounter-to-patient-folder assignment

1. Extend the transaction in `startEncounterForCalendarEvent`.
2. Resolve the patient before creating the note.
3. Reuse the patient profile and folder when the email already exists.
4. Otherwise create the private patient folder and profile atomically.
5. Create the encounter note directly in that folder.
6. Preserve the existing idempotency behavior so retrying an encounter cannot create duplicate notes, profiles, or folders.
7. Keep unresolved encounters in `Meetings` or `Unassigned` and expose an explicit manual assignment path.

### Phase 4 — Note format and clinical output

1. Keep the canonical transcript in the existing note/transcript fields.
2. Add a short encounter focus output, separate from SOAP and the longer summary.
3. At completion, use a safe title format such as `2026-08-14 — Medication follow-up`.
4. Only update an automatically created note if the user has not manually edited its title/body.
5. Add a one-line body or metadata field such as `Addressed: medication response and blood-pressure follow-up.` without overwriting user-authored content.
6. Preserve the existing summary/SOAP generation and retry/stale behavior.

### Phase 5 — UI and review workflow

1. Show the resolved patient name/email on encounter cards and the note header.
2. Show an `Unassigned` or `Needs review` state when automatic assignment was not safe.
3. Add `Assign patient` and `Create new patient` actions.
4. Make the first automatic assignment visibly confirmable, especially when the source is a structured description fallback.
5. Allow folder renames without changing patient identity.

### Phase 6 — Existing data and rollout

1. Do not automatically reclassify historical notes by name.
2. Provide a preview-only backfill that reports candidate email matches and conflicts.
3. Require confirmation before moving historical notes into patient folders.
4. Roll out new encounters first, with a feature flag or settings toggle if needed.
5. Log assignment reason and unresolved reason without logging full transcripts or raw descriptions.

## Acceptance criteria

- Starting the same calendar encounter twice creates one note, one patient profile, and one patient folder.
- Two encounters with the same normalized email reuse the same patient folder even if the display name changes.
- The same display name with two different emails creates two separate patient profiles/folders.
- A multi-attendee encounter is not auto-assigned to a patient.
- An encounter with no trustworthy email remains unassigned.
- A conflicting attendee email and structured-description email is not auto-assigned.
- Patient folder creation never targets a team/shared space automatically.
- Raw calendar descriptions do not cross the bridge into the renderer.
- A completed note has a date-first title and concise focus when generation succeeds, while the transcript remains intact.
- User-edited note content/title is not overwritten by completion-time formatting.
- Existing encounter, clinical-output, note-folder, and calendar synchronization tests remain green.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Calendar invite is a caregiver, coordinator, or group rather than the patient | Require exactly one external attendee and provide review/assignment UI |
| Name collision or display-name change | Match only on normalized email; folder name is mutable presentation data |
| Description contains stale or malicious metadata | Parse a bounded labeled block, validate values, detect conflicts, and never use free-form text |
| PHI appears in shared content | Create patient folders only in the private space by default |
| Generated focus overwrites user work | Update only untouched auto-created drafts |
| Provider-specific calendar differences | Normalize through the shared calendar contract and test Google, Microsoft, and Apple shapes |

## Verification plan

- Unit: identity normalization, structured metadata parser, conflict handling, attendee filtering, and note-title formatting.
- Database integration: profile/folder uniqueness, transaction rollback, idempotent encounter starts, private-space enforcement, and migration behavior.
- Bridge integration: sanitized structured metadata is returned; raw description is not returned; Google attendee email remains available.
- UI tests: assigned, unassigned, conflict, manual assignment, and patient-folder navigation states.
- End-to-end scenarios: repeat Alex Morgan encounter, changed name with same email, same name with different email, group encounter, missing email, and description fallback.
- Observability: assignment reason is logged as structured metadata without raw PHI.
